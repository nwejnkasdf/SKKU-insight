## 3.1 External Interface Requirements

### 3.1.1 User Interfaces (Table 4)

#### UI-01. 온보딩 화면

![Wireframe 1. Onboarding](../../assets/wire_01_onboarding.png)

| 항목 | 내용 |
|---|---|
| 목적 | 계정 생성, 개인화 데이터 수집 동의, 초기 관심 분야 선택을 처리한다. |
| 사용자 | 이공계 학생, 연구자, 교수 |
| 주요 입력 | 일반 이메일, 비밀번호, 관심 분야 선택, 데이터 수집 동의 |
| 주요 출력 | 초기 관심 상태 생성 결과 |
| 전환 | 완료 후 대시보드 화면으로 이동 |
| 빈 상태 | 관심 분야를 선택하지 않으면 시작 버튼을 비활성화한다. |
| 오류 상태 | 이메일/비밀번호 인증 실패 또는 동의 미완료 시 진행할 수 없다는 안내를 표시한다. |

온보딩 화면은 사용자가 넓은 관심 분야를 선택할 수 있도록 한다. 시스템은 선택된 관심 분야를 CSO 상위 토픽으로 매핑한다. 사용자는 개인화 로그 수집 목적을 확인하고 동의해야 하며, 동의하지 않으면 회원가입 또는 초기 설정을 완료할 수 없다.

#### UI-02. 대시보드 화면

![Wireframe 2. Dashboard](../../assets/wire_02_dashboard.png)

| 항목 | 내용 |
|---|---|
| 목적 | 사용자별 최신 기술 동향 추천 10개를 표시한다. |
| 사용자 | 이공계 학생, 연구자, 교수 |
| 주요 입력 | 추천 카드 클릭, 저장, 숨김, 관심 없음 |
| 주요 출력 | core 5개, adjacent 3개, discovery 2개 추천 카드 |
| 전환 | 토픽 상세 또는 문서 상세 화면으로 이동 |
| 빈 상태 | 추천 후보가 부족하면 토픽 인접 범위와 신뢰 소스 전체 트렌드로 fallback을 확장해 10개를 채운다. |
| 오류 상태 | 서버 오류 시 마지막으로 캐시된 추천과 재시도 안내를 표시한다. |

대시보드 화면은 앱 실행 시 최신 추천 목록을 표시한다. 초기 버전에서 추천 카드는 후보가 충분한 경우 `core`, `adjacent`, `discovery`가 5:3:2 목표 비율로 구성된다. 후보가 부족하면 슬롯 대체와 fallback을 적용하되 총 10개 카드를 유지한다. 각 카드는 제목, 출처, 소스 유형, 관련 토픽, 간단한 추천 이유를 표시한다.

#### UI-03. 토픽 상세 화면

![Wireframe 3. Topic Detail](../../assets/wire_03_topic_detail.png)

| 항목 | 내용 |
|---|---|
| 목적 | 특정 상위 토픽 또는 동적 리프 토픽의 흐름을 보여준다. |
| 사용자 | 이공계 학생, 연구자, 교수 |
| 주요 입력 | 토픽 선택, 관련 문서 선택 |
| 주요 출력 | 관련 문서, 하위 리프 토픽, 최근 동향 |
| 전환 | 문서 상세 화면으로 이동 |
| 빈 상태 | 관련 최신 문서가 없으면 인접 토픽의 공식 소스를 안내한다. |
| 오류 상태 | 토픽 연결 오류 시 오류 안내와 대시보드 복귀 기능을 제공한다. |

토픽 상세 화면은 상위 토픽, 연결된 동적 리프 토픽, 최신 문서 목록을 표시한다. 동적 리프 토픽은 `emerging`, `active`, `stale`, `merged` 상태 중 하나로 관리된다.

#### UI-04. 문서 상세 화면

![Wireframe 4. Document Detail](../../assets/wire_04_document_detail.png)

| 항목 | 내용 |
|---|---|
| 목적 | 추천 문서의 상세 정보, 섹션형 생성 요약, 짧은 토픽 근거를 표시한다. |
| 사용자 | 이공계 학생, 연구자, 교수 |
| 주요 입력 | 저장, 숨김, 관심 없음, 외부 원문 열기 |
| 주요 출력 | 문서 요약, 원문 링크, 추천 슬롯, 관련 토픽 |
| 전환 | 원문 브라우저 또는 이전 화면 |
| 빈 상태 | 생성 요약이 없으면 출처가 제공한 초록 또는 설명을 표시한다. |
| 오류 상태 | 원문 링크 접근 실패 시 출처명과 재시도 안내를 표시한다. |

문서 상세 화면은 문서의 출처, 요약, 관련 상위 토픽, 동적 리프 토픽, 추천 슬롯을 제공한다. 추천 이유는 짧은 토픽 근거 수준으로 제한하며 사용자의 행동 로그나 관심 점수는 노출하지 않는다.

#### UI-05. 설정/피드백 화면

![Wireframe 5. Settings & Feedback](../../assets/wire_05_settings.png)

| 항목 | 내용 |
|---|---|
| 목적 | 개인화 설정, 관심 분야, 계정 및 데이터 삭제 요청을 관리한다. |
| 사용자 | 이공계 학생, 연구자, 교수 |
| 주요 입력 | 관심 분야 수정, 데이터 수집 동의 확인 또는 철회, 계정 삭제 요청 |
| 주요 출력 | 설정 변경 결과 |
| 전환 | 대시보드 화면 |
| 빈 상태 | 저장/숨김 문서가 없으면 목록 대신 안내 문구를 표시한다. |
| 오류 상태 | 삭제 요청 실패 시 재시도 안내와 고객 지원 안내를 표시한다. |

설정/피드백 화면은 사용자가 관심 분야를 수정하고 개인화 데이터 수집 동의 상태를 확인하거나 철회할 수 있도록 한다. 필수 개인화 동의를 철회하면 추천 대시보드와 개인화 기능은 중단되고, 사용자는 재동의 또는 계정 삭제를 선택할 수 있다. 사용자는 계정 삭제와 함께 행동 로그, 관심 상태, 저장/숨김 기록 삭제를 요청할 수 있다.

#### UI-06. 관리자 웹 콘솔

![Wireframe 6. Admin Web Console](../../assets/wire_06_admin.png)

| 항목 | 내용 |
|---|---|
| 목적 | 별도 내부 웹 콘솔에서 수집, 필터링, 토픽 연결 상태를 확인한다. |
| 사용자 | 관리자 |
| 주요 입력 | 관리자 로그인, 실패 작업 재실행 요청, 로그 필터링 |
| 주요 출력 | 수집 상태, 실패 로그, 낚시성 탐지 통계, 토픽 연결 오류 |
| 전환 | 관리자 세부 로그 화면 |
| 빈 상태 | 실패 작업이 없으면 정상 운영 상태를 표시한다. |
| 오류 상태 | 재실행 요청 실패 시 작업 ID와 오류 메시지를 표시한다. |

관리자 웹 콘솔은 추천 후보를 수동으로 큐레이션하지 않는다. 대신 자동화된 백엔드의 동작 상태를 확인하고 실패한 작업의 재실행을 요청한다. 관리자 웹 콘솔은 일반 사용자용 Windows 앱과 분리되며, 일반 사용자 계정과 별도의 관리자 권한을 요구한다.

### 3.1.2 Hardware Interfaces

시스템은 사용자의 Windows 데스크톱 또는 노트북 PC에서 동작한다. 별도 특수 하드웨어는 요구하지 않는다.

### 3.1.3 Software Interfaces

| 인터페이스 | 설명 |
|---|---|
| 인증 API | 일반 이메일 및 비밀번호 기반 계정 생성과 로그인 |
| 동의 관리 API | 개인정보 및 개인화 데이터 수집 동의 상태 관리 |
| 관심 상태 API | 사용자별 상위 토픽 및 리프 토픽 관심 상태 조회/갱신 |
| 추천 API | 사용자별 추천 대시보드 데이터 제공 |
| 소스 수집 API | 외부 문서 수집 작업 실행 및 상태 조회 |
| 낚시성 탐지 API | 뉴스/기사성 2차 문서의 낚시성 여부 판별 |
| 관리자 API | 관리자 웹 콘솔 인증, 수집 상태, 실패 로그, 통계, 재실행 요청 처리 |
| 계정 삭제 API | 사용자 계정과 개인화 데이터 삭제 요청 처리 |

### 3.1.4 Communication Interfaces

- 클라이언트와 서버는 HTTPS 기반 통신을 사용한다.
- 사용자의 행동 로그는 동의 상태가 유효한 경우에만 서버 API로 전송된다.
- 서버는 사용자 관심 상태와 추천 결과를 클라이언트에 반환한다.
- 관리자 웹 콘솔은 서버의 운영 모니터링 API와 통신한다.

## 3.2 Functional Requirements (Table 5)

### 3.2.1 User Account

| ID | 요구사항 |
|---|---|
| FR-01 | 시스템은 사용자에게 일반 이메일과 비밀번호 기반 회원가입 기능을 제공해야 한다. |
| FR-02 | 시스템은 등록된 사용자에게 일반 이메일과 비밀번호 기반 로그인 기능을 제공해야 한다. |
| FR-03 | 시스템은 로그인한 사용자와 관심 상태, 피드백, 설정 데이터를 연결해야 한다. |
| FR-04 | 시스템은 사용자가 로그아웃할 수 있는 기능을 제공해야 한다. |
| FR-05 | 시스템은 개인화 데이터 수집 동의를 완료하지 않은 사용자의 회원가입 또는 초기 설정 완료를 차단해야 한다. |
| FR-06 | 시스템은 사용자가 계정과 개인화 데이터 삭제를 요청할 수 있도록 해야 한다. |

### 3.2.2 Onboarding

| ID | 요구사항 |
|---|---|
| FR-07 | 시스템은 최초 로그인 사용자에게 온보딩 화면을 제공해야 한다. |
| FR-08 | 시스템은 사용자에게 넓은 관심 분야 선택지를 제공해야 한다. |
| FR-09 | 시스템은 사용자가 선택한 관심 분야를 CSO 상위 토픽으로 매핑해야 한다. |
| FR-10 | 시스템은 온보딩에서 행동 로그 및 관심 상태 데이터 수집 목적을 안내해야 한다. |
| FR-11 | 시스템은 사용자가 데이터 수집에 동의한 경우에만 회원가입 또는 초기 설정을 완료해야 한다. |

### 3.2.3 Interest State Inference

| ID | 요구사항 |
|---|---|
| FR-12 | 시스템은 사용자의 관심 상태를 CSO 상위 토픽과 동적 리프 토픽의 이원화 구조로 관리해야 한다. |
| FR-13 | 시스템은 CSO를 넓고 안정적인 상위 토픽 좌표계로 사용해야 한다. |
| FR-14 | 시스템은 사용자별 에이전트를 통해 최신 자료에서 세부 동적 리프 토픽을 생성하거나 기존 상위 토픽에 연결해야 한다. |
| FR-15 | 시스템은 동적 리프 토픽을 `emerging`, `active`, `stale`, `merged` 상태로 관리해야 한다. |
| FR-16 | 시스템은 모든 동적 리프 토픽을 하나 이상의 상위 CSO 토픽에 연결해야 한다. |
| FR-17 | 시스템은 클릭, 체류, 재방문, 저장, 숨김, 관심 없음 신호를 관심 상태 추론 입력으로 사용해야 한다. |
| FR-18 | 시스템은 암묵 행동 로그를 관심 상태 업데이트의 주된 신호로 사용해야 한다. |
| FR-19 | 시스템은 사용자의 저장, 숨김, 관심 없음 입력을 최소 명시 피드백으로 반영해야 한다. |
| FR-20 | 시스템은 관심 상태에 시간 감쇠를 적용해 오래된 관심 신호의 영향력을 줄여야 한다. |

### 3.2.4 Source Collection

| ID | 요구사항 |
|---|---|
| FR-21 | 시스템은 각 사용자 관심 토픽에 맞는 기술 동향 자료를 사용자별 수집 작업으로 일 1회 수집해야 한다. |
| FR-22 | 시스템은 학술지/논문, 빅테크 공식 채널, 테크 뉴스를 기본 수집 소스로 사용해야 한다. |
| FR-23 | 시스템은 학술 소스를 학술지, 논문 데이터베이스, 학회 proceedings 범주로 관리해야 한다. |
| FR-24 | 시스템은 빅테크 공식 채널에 기업 공식 블로그, 공식 연구 블로그, 릴리즈 노트, 공식 문서, 컨퍼런스 발표를 포함해야 한다. |
| FR-25 | 시스템은 테크 뉴스를 학술 소스 및 빅테크 공식 채널과 동등한 추천 후보로 취급하되, 뉴스/기사성 2차 문서는 낚시성 필터 통과를 필수 조건으로 해야 한다. |
| FR-26 | 시스템은 최종 랭킹에서 사용자 관심 토픽 적합도를 1순위 기준으로 사용해야 한다. |
| FR-27 | 시스템은 수집된 문서를 상위 토픽과 동적 리프 토픽에 연결해야 한다. |
| FR-28 | 시스템은 동일 URL, DOI, 또는 제목 유사도가 높은 문서를 중복 추천하지 않아야 한다. |
| FR-29 | 시스템은 사용자별 소스 수집 실패를 기록하고 관리자 웹 콘솔에 표시해야 한다. |

| Precondition | 관리자가 별도 관리자 웹 콘솔에 관리자 계정으로 로그인했고 실패 작업이 기록되어 있다. |
| Main Flow | 1. 관리자는 관리자 웹 콘솔에 접속한다. 2. 시스템은 수집 상태, 실패 로그, 낚시성 탐지 통계, 토픽 연결 오류를 표시한다. 3. 관리자는 실패 작업을 선택한다. 4. 관리자는 재실행을 요청한다. 5. 시스템은 재실행 요청자, 대상 작업, 요청 시각, 상태를 기록하고 작업 상태를 갱신한다. |
| Exception Flow | 관리자 권한이 없으면 접근을 차단한다. 재실행 요청이 실패하면 시스템은 작업 ID와 오류 메시지를 표시한다. |
| Related FR | FR-60, FR-61, FR-62, FR-63, FR-64, FR-65 |
